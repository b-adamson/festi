# point_sampler

A hardware accelerator for the point-on-triangle math in festi's procedural
instancing system -- the code that scatters instanced meshes (random
scatter, and the "building" column/strut generator) across a parent
model's surface. Specifically, this reimplements the last line of
`addRndInstance()` in [`src/model.cpp`](../../src/model.cpp):

```cpp
instanceTransform.translation += (1.0f - u - v) * v0 + u * v1 + v * v2;
```

i.e. barycentric interpolation: given a triangle (`v0, v1, v2`) and a
sample `(u, v)`, compute the corresponding point. This is also, not
coincidentally, the same math a GPU rasterizer uses to interpolate vertex
attributes across a triangle -- so the core (`rtl/barycentric.sv`) doubles
as a first building block toward a from-scratch rasterizer.

Two hardware paths exist: a JTAG/VIO debug path for bring-up (§2), and an
AXI4-Lite + embedded-Linux path (§3) that's how the engine actually talks
to the board day-to-day, via `hw/uio_bridge.py` and `hw/dashboard_server.py`.

## Layout

```
rtl/       fixed_pkg.sv (Q16.16 fixed-point types), barycentric.sv (the core), barycentric_axi.sv (AXI wrapper)
sim/       tb_barycentric.sv, tb_barycentric_axi.sv -- file-driven SystemVerilog testbenches
scripts/   gen_vectors.py (golden model + test vectors), compare.py, run_sim.ps1, run_sim_axi.ps1
hw/        FPGA bring-up, block design, on-board bridge, dashboard (see below)
vectors/   generated test vectors + sim results (gitignored, regenerated by run_sim.ps1)
```

## Fixed-point format

Everything is Q16.16 signed fixed-point (32-bit, 16 fractional bits) --
see `rtl/fixed_pkg.sv`. To convert by hand: `fixed = round(real * 65536)`,
and as hex, `10.0 -> 0x000A0000`, `0.25 -> 0x00004000`, `-0.3 -> 0xFFFFB333`
(two's complement).

## 1. Simulation-only verification (no hardware needed)

`rtl/barycentric.sv` is a 3-stage pipelined core computing
`out = w*v0 + u*v1 + v*v2` (`w = 1-u-v`), checked against an independent
Python golden model (`scripts/gen_vectors.py`) via Vivado's `xsim`:

```
cd fpga/point_sampler
powershell -File scripts\run_sim.ps1
```

Regenerates 200 random vectors, runs the testbench, diffs against the
golden model, prints `PASS`/`FAIL` with max error (expect ~0.01, Q16.16
truncation noise, not a bug). `run_sim_axi.ps1` does the same for the AXI
wrapper (`sim/tb_barycentric_axi.sv`), prints `ALL GOOD` on a pass.

## 2. JTAG/VIO bring-up path

`hw/barycentric_vio_top.sv` wraps the core with a Xilinx VIO debug core,
driven entirely over JTAG -- no external pins, no board-specific
constraints. Clock is `STARTUPE3`'s `CFGMCLK` (UltraScale+'s internal
post-configuration oscillator).

```
vivado -mode batch -source hw/build_and_program.tcl   # build + synth + program
vivado -mode batch -source hw/live_demo.tcl            # reprogram + run 5 test cases, PASS/FAIL table
vivado -mode batch -source hw/test_live.tcl            # same read/write dance, for debugging
```

**Windows path-length note**: Vivado's `dbg_hub` generation fails past
~146 characters of working path. Work around with a drive mapping rather
than moving the project: `subst V: "C:\path\to\festi\fpga\point_sampler"`,
build from `V:\` (`subst V: /d` to undo).

Or drive it by hand: Vivado Hardware Manager -> open target -> **Probes
File** -> `hw/vivado_proj/barycentric_vio.runs/impl_1/barycentric_vio_top.ltx`
-> add probes in `hw_vios` -> edit/commit/refresh.

This path is for bring-up only -- JTAG needs a laptop physically attached
and reprogrammed after every power cycle. §3 is the real deployment path.

## 3. AXI4-Lite + embedded-Linux path

`rtl/barycentric_axi.sv` wraps the core with an AXI4-Lite slave so it sits
in the ARM cores' own memory map as ordinary MMIO -- no JTAG cable needed
once it's loaded.

### Register map

16 registers, 4-byte stride (`0x00`-`0x3C`), all Q16.16 except CTRL/STATUS:

| Offset | Register | R/W | Meaning |
|--------|----------|-----|---------|
| `0x00`/`0x04`/`0x08` | `V0X`/`V0Y`/`V0Z` | RW | Triangle vertex 0 |
| `0x0C`/`0x10`/`0x14` | `V1X`/`V1Y`/`V1Z` | RW | Triangle vertex 1 |
| `0x18`/`0x1C`/`0x20` | `V2X`/`V2Y`/`V2Z` | RW | Triangle vertex 2 |
| `0x24` / `0x28` | `U` / `V` | RW | Sample coordinates |
| `0x2C` | `CTRL` | WO | bit 0 = start (self-clearing) |
| `0x30` | `STATUS` | RO | bit 0 = done |
| `0x34`/`0x38`/`0x3C` | `OUTX`/`OUTY`/`OUTZ` | RO | Result point |

Usage: write the 11 inputs, strobe `CTRL`, poll `STATUS`, read the outputs.

### Block design

`hw/build_axi_bd.tcl` packages `barycentric_axi.sv` as an IP-XACT core and
wires it into a Zynq UltraScale+ PS block design:

```
zynq_ps (M_AXI_HPM0_FPD) -> axi_smc (1x1 SmartConnect) -> barycentric_axi_0 (s_axi)
```

plus a `proc_sys_reset` off the PS's own reset. Only `PSU__USE__M_AXI_GP0`
is enabled -- board-preset automation also wants a second GP master
(`M_AXI_HPM0_LPD`) that comes up clockless in this design, so it's
explicitly disabled.

```
cd fpga/point_sampler
vivado -mode batch -source hw/build_axi_bd.tcl
```

Prints `BD_BUILD_OK` and the bitstream path on success. Peripheral address
(4KB window) is assigned by Vivado's address editor -- check the script's
`== Assigned address segments ==` output rather than assuming a fixed base.

### Loading it onto the K26

The K26's Ubuntu image expects new PL logic as an "accelerator platform"
overlay, loaded live via `xmutil` (no reboot, doesn't disturb the running
OS). `hw/overlay/` builds that package:

1. **`point_sampler.bit.bin`** -- the bitstream with its header stripped
   (`bootgen -image point_sampler.bif -arch zynqmp -process_bitstream bin`).
2. **`point_sampler.dtbo`** -- device-tree overlay (`point_sampler.dtsi`,
   compiled with `cpp | dtc -@`) that loads the bitstream via `&fpga_full`
   and exposes the peripheral as a plain `/dev/uioN` device at its assigned
   address (`generic-uio` compatible) -- no XRT/zocl involved, since this
   is a raw register block, not a Vitis kernel.
3. **`shell.json`** -- `{"shell_type": "XRT_FLAT", "num_slots": "1"}`.

On the board:
```
sudo mkdir -p /lib/firmware/xilinx/point_sampler
sudo cp point_sampler.bit.bin point_sampler.dtbo shell.json /lib/firmware/xilinx/point_sampler/
sudo xmutil unloadapp        # only one XRT_FLAT app can be loaded at a time
sudo xmutil loadapp point_sampler
```
`xmutil listapps` shows `point_sampler` with a real slot handle once
loaded. The board's default accelerator (e.g. `k26-starter-kits`) must be
unloaded first to free the slot.

### The bridge: `hw/uio_bridge.py` + `hw/dashboard_server.py`

`uio_bridge.py` runs persistently on the board (`sudo python3 uio_bridge.py`),
opens `/dev/uioN` once via `mmap`, and listens on TCP port 9765: one line
in (`"v0x v0y v0z v1x v1y v1z v2x v2y v2z u v"`, decimal floats), one line
out (`"x y z"`). `dashboard_server.py` runs on the dev machine, serves
`dashboard.html` at `http://localhost:8765`, and forwards both its
`/api/query` and `/api/batch` endpoints to the bridge over a plain
ethernet link to the board (`BRIDGE_HOST`/`BRIDGE_PORT` at the top of the
file) -- this is also what `queryFpgaBatch()` in `src/model.cpp` talks to,
so the engine needs no code changes to use real hardware.

```
python hw/dashboard_server.py     # on the dev machine
```

A serial link (the board's JTAG/UART console) also works as a fallback
transport if ethernet isn't available, but is ~10-20x slower (a 115200-baud
debug console, not a data link) -- expect single-digit ms per instance
over ethernet vs tens of ms over serial.

Set `FESTI_FORCE_CPU_INSTANCING=1` before launching festi.exe to skip the
FPGA path entirely and always use the CPU formula, regardless of whether
the board/bridge are reachable.
